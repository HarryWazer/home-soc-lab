## Detection

Multiple failed authentication attempts against a local Windows account, followed by a successful logon from the same source, consistent with a brute force password-guessing attack.

- **Rule ID:** 60122 — *"Logon Failure - Unknown user or bad password"* (Windows Event ID 4625)
- **Rule level:** 5
- **Total failed login events:** 8 (first batch), plus additional attempts in the second test run
- **Successful login:** 1, following the failed attempts, same source IP

## Analysis

The target account `vboxuser` was configured with a weak password identical to the username itself, which allowed the brute force attack to succeed within a very small wordlist (6 entries). This is a textbook example of a credential weakness that would be trivially broken by any automated password-guessing tool, even without a large dictionary.

The Wazuh out-of-the-box ruleset correctly logged each individual failed logon attempt (rule 60122) and the eventual successful logon, but **did not automatically escalate severity** based on the volume of failed attempts from a single source IP in a short time window. In a production environment, this gap would typically be addressed with:

- A custom correlation rule that raises severity when N failed logons from the same source IP occur within a defined time window (e.g., >5 failures in 5 minutes)
- Active Response configured to temporarily block the source IP after repeated failures
- Account lockout policy enforcement at the OS level

It was also observed during testing that an active local (console) RDP session for the same user account blocks a second concurrent RDP session — a native Windows desktop-edition behavior, not a security control, but worth noting as it affects attack reliability/timing in this lab.

## Recommended Actions

1. Enforce strong, unique passwords for all local accounts (never identical to the username).
2. Implement account lockout policy after a small number of failed attempts.
3. Restrict RDP access to specific trusted source IPs via firewall rules, or disable direct RDP exposure and require VPN/jump-host access instead.
4. Create a custom Wazuh correlation rule to escalate severity on repeated authentication failures from a single source within a short window.
5. Enable Wazuh Active Response to automatically block source IPs exhibiting brute force behavior.
6. Consider enabling Network Level Authentication (NLA) in production (it was intentionally disabled in this lab only to allow testing with an experimental brute-force tool).

## Lessons Learned (Lab Notes)

- THC-Hydra's RDP module is explicitly experimental and proved unreliable in this environment; `xfreerdp` was used to validate connectivity and credentials independently before re-running Hydra.
- NLA (Network Level Authentication) had to be temporarily disabled on the target for the brute force tool to establish a connection — a configuration change that would **not** be recommended outside of a controlled test.
- VirtualBox snapshots reset registry/service changes (RDP enablement, NLA settings); a dedicated `win11-rdp-ready` snapshot was created after reconfiguration to avoid repeating these steps for future scenarios.
