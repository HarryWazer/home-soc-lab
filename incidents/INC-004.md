## Detection

A new scheduled task was created on the victim host using a disguised, legitimate-sounding name, configured to run a hidden PowerShell command on a daily schedule — a classic persistence technique used to maintain access across reboots and logoffs.

- **Rule ID:** 60228 — *"A scheduled task was created"* (Windows Event ID 4698)
- **Rule level:** 4
- **Detection mechanism:** Windows Security Auditing, subcategory *"Other Object Access Events"* (not enabled by default; had to be explicitly enabled via `auditpol`)

## Technique Simulated

A scheduled task named **`WindowsUpdateCheck`** was created — intentionally mimicking a legitimate Windows Update process name to avoid drawing attention — configured as follows:

```
schtasks /create /tn "WindowsUpdateCheck" /tr "powershell.exe -WindowStyle Hidden -Command Get-Date" /sc daily /st 09:00
```

- **Trigger:** Daily, starting at 09:00
- **Action:** `powershell.exe -WindowStyle Hidden -Command Get-Date` (benign placeholder for this test; in a real attack this would be a command to re-establish C2 communication, re-download a payload, or re-execute malware)
- **Window style:** Hidden, so no visible window would alert the user

## Analysis

The Wazuh out-of-the-box ruleset correctly detected and classified the scheduled task creation, and — notably — tagged it with **three simultaneous MITRE ATT&CK tactics** (Execution, Persistence, Privilege Escalation) under the single technique T1053 (Scheduled Task/Job). This reflects the dual-use nature of scheduled tasks: they provide a mechanism to both *execute* code and *persist* it across reboots/logoffs, and — depending on the task's configured run-as context (e.g., `SYSTEM`) — can also be leveraged for privilege escalation.

A key finding is that **this detection was only possible because the relevant Windows audit subcategory was explicitly enabled beforehand** (`auditpol /set /subcategory:"Other Object Access Events" /success:enable /failure:enable`). On a default Windows 11 installation, Event ID 4698 is not generated at all, meaning scheduled-task-based persistence would be completely invisible to a SIEM relying only on default Windows auditing — regardless of how well the SIEM's own detection rules are tuned. This mirrors the same visibility gap identified in INC-002 for PowerShell Script Block Logging: **detection rules are only as good as the underlying log sources feeding them.**

The full task XML captured in `taskContent` provided complete visibility into what the task would execute, when, and as whom — information that would be critical in a real investigation to assess the actual payload and blast radius, rather than relying solely on the task name (which, as demonstrated here, can be deliberately misleading).

## Recommended Actions

1. Enable the *"Other Object Access Events"* audit subcategory (and related scheduled-task auditing) as a **baseline configuration** on all monitored Windows endpoints, not as an opt-in afterthought.
2. Create a Wazuh active response or alerting rule to flag scheduled tasks whose action involves `powershell.exe`, `cmd.exe`, `wscript.exe`, `mshta.exe`, or other common living-off-the-land binaries, especially when combined with hidden window styles or encoded arguments.
3. Maintain an inventory/baseline of expected scheduled tasks per host, so that newly created tasks with unfamiliar or suspiciously generic names (e.g., mimicking "WindowsUpdate", "SystemCheck") are flagged for manual review.
4. Correlate scheduled task creation events with the parent process and logon session that created them (`subjectLogonId`, `clientProcessId`) to help distinguish legitimate administrative activity from attacker-driven persistence.
5. Periodically audit and remove scheduled tasks created outside of approved change-management processes.

## Lessons Learned (Lab Notes)

- Windows Event ID 4698 (scheduled task creation) is **not logged by default** and requires explicitly enabling the *"Other Object Access Events"* audit subcategory via `auditpol`.
- After enabling auditing, the original scheduled task had to be deleted and recreated for a corresponding event to be generated — auditing changes do not apply retroactively to actions that already occurred.
- The task's full XML definition (including trigger schedule and author) was captured in a single event field (`taskContent`), providing rich context without needing to cross-reference multiple log sources — a notably convenient aspect of this particular Windows event.
