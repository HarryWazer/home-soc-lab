## Detection

Port scanning and OS/service fingerprinting activity was performed against the victim host from the attacker machine. The activity was successfully **blocked** by the Windows Firewall and recorded in its native log file, but it was **not detected or alerted on by Wazuh**, despite the agent actively ingesting the relevant log file. This incident documents both the attack and the detection gap itself.

## Technique Simulated

Two scans were run from the Kali attacker machine:

1. **Port sweep with version detection:**
   ```
   nmap -sV -p 1-1000 192.168.56.20
   ```
   Result: all 1000 scanned ports reported as `filtered` — the Windows Firewall silently dropped all probes in this range.

2. **Aggressive scan (OS detection, version detection, scripts, traceroute):**
   ```
   nmap -A 192.168.56.20
   ```
   Result: port **3389/tcp (RDP)** was found open, and Nmap's `rdp-ntlm-info` and `ssl-cert` scripts extracted significant information directly from the RDP service banner/TLS handshake, **without needing a successful login**:
   - Hostname: `WIN11-VICTIM`
   - NetBIOS domain and computer name
   - Windows product version: `10.0.26100` (Windows 11)
   - SSL certificate validity dates
   - Target system time (useful for clock-skew-based attack timing)
   - OS fingerprint: Microsoft Windows 10/11

## Evidence

- **Windows Firewall log** (`C:\Windows\System32\LogFiles\Firewall\pfirewall.log`), filtered to the attacker's IP:
  ```
  Get-Content "C:\Windows\System32\LogFiles\Firewall\pfirewall.log" | Select-String "192.168.56.30"
  ```
  Showed multiple `DROP TCP` entries on ports 445, 139, and 135 (SMB/RPC probes) and multiple `DROP ICMP` entries (type 8 — echo request, used in Nmap's host discovery), all timestamped to match the two scan runs.

## Analysis

This scenario produced a **negative detection result**, which is itself the primary finding.

**Confirmed: the host firewall worked as a preventive control.** All 1000 ports scanned in the first run were filtered, and even in the second, more aggressive scan, only the intentionally-exposed RDP port responded. This is consistent with INC-001, where RDP was deliberately kept open and became the entry point for a successful brute force attack — reconnaissance here effectively re-confirmed the same exposed attack surface.

**Confirmed: the exposed RDP service itself leaks reconnaissance-relevant information** (hostname, domain, OS version, certificate dates) via unauthenticated protocol-level banners, before any credentials are needed. An attacker does not need a successful login to begin profiling the target.

**Key detection gap identified:** although Windows Firewall logging was explicitly enabled (`Set-NetFirewallProfile -LogBlocked True`) and the Wazuh agent was configured to monitor the resulting log file (confirmed in `ossec.log`: *"Analyzing file: ... pfirewall.log"*), **no corresponding alerts, or even raw log entries, appeared in the Wazuh dashboard.** This was investigated and traced to a **decoder gap**: Wazuh's default ruleset does not ship with a decoder capable of parsing the native Windows Firewall log format (a W3C-extended-log-file-style format), so even though the agent reads and forwards the file, the server-side pipeline has no rule to interpret or index its contents.

This differs from the detection gaps identified in INC-002 and INC-003, which were caused by **disabled Windows audit/logging settings** (a configuration problem, fixable by enabling the right setting). This gap is caused by a **missing decoder/rule on the Wazuh server side** — a tooling limitation that cannot be fixed by endpoint configuration alone, and would require either custom decoder/rule development or a different monitoring approach entirely (see Recommended Actions).

This is an important, realistic SOC lesson: **enabling a log source is necessary but not sufficient for detection** — the SIEM must also have a decoder/rule capable of understanding that log's format, or the data is collected for nothing.

## Recommended Actions

1. Develop a custom Wazuh decoder and rule set for the native Windows Firewall log format (`pfirewall.log`), to parse `DROP`/`ALLOW` entries and generate alerts on patterns indicative of scanning (e.g., many distinct destination ports from one source IP in a short window).
2. As a more scalable alternative to parsing local firewall logs, deploy a network-based detection capability (e.g., Suricata integrated with Wazuh, or a dedicated NIDS/NTA sensor) at a network chokepoint, since host-based agents alone have fundamental blind spots for traffic that does not reach an application-layer log.
3. Restrict RDP exposure to only the hosts/networks that require it, and disable or firewall off protocol-level information disclosure where possible (e.g., via RDP connection restrictions, Network Level Authentication, or placing RDP behind a VPN/jump host) to reduce the value of banner-grabbing reconnaissance.
4. Periodically validate that "logging enabled" configurations (NTFS auditing, firewall logging, PowerShell logging, etc.) actually result in **indexed, alertable data** in the SIEM — not just confirm that the agent is reading the file, as collection without correct decoding provides a false sense of security.
5. Consider rate-based or threshold-based detection at the firewall/network layer (e.g., many connection attempts to many different ports from the same source within seconds) as a decoder-independent fallback for scan detection.

## Lessons Learned (Lab Notes)

- Nmap's `-A` flag extracted meaningful host information (hostname, domain, OS version, certificate validity) from a single open RDP port without any authentication — a reminder that even a single exposed service carries reconnaissance value.
- Enabling Windows Firewall logging (`Set-NetFirewallProfile -LogBlocked True`) and confirming the Wazuh agent is actively reading the resulting file (via `ossec.log`) is **not sufficient proof that detection will work** — the full pipeline (agent → server → decoder → rule → index) must be validated end-to-end.
- This lab's default Wazuh ruleset has strong, out-of-the-box coverage for Windows Event Log-based telemetry (as seen in INC-001 through INC-003) but has a clear gap for native Windows Firewall text logs, which would need custom decoder development to close.
- This scenario is a useful contrast to the previous three: in INC-002 and INC-003, enabling a built-in Windows audit setting was sufficient to unlock detection. In INC-004, enabling the log source was not sufficient — demonstrating that not all "visibility gaps" have the same root cause or the same fix.
