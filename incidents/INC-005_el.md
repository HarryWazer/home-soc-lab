# INC-004: Αναγνώριση Δικτύου (Network Reconnaissance) κατά του WIN11-VICTIM

## Εντοπισμός

Πραγματοποιήθηκε σάρωση θυρών και αναγνώριση OS/υπηρεσιών (fingerprinting) κατά του μηχανήματος-θύματος από το μηχάνημα του επιτιθέμενου. Η δραστηριότητα **μπλοκαρίστηκε επιτυχώς** από το Windows Firewall και καταγράφηκε στο δικό του αρχείο log, αλλά **δεν εντοπίστηκε ούτε δημιούργησε alert στο Wazuh**, παρόλο που ο agent διάβαζε ενεργά το σχετικό αρχείο log. Αυτό το περιστατικό καταγράφει τόσο την επίθεση όσο και το ίδιο το κενό εντοπισμού.

## Πηγή και Στόχος

| Ρόλος | Hostname | Διεύθυνση IP |
|---|---|---|
| **Επιτιθέμενος** | Kali-Attacker | 192.168.56.30 |
| **Στόχος** | WIN11-VICTIM | 192.168.56.20 |
| **Εργαλείο που χρησιμοποιήθηκε** | Nmap 7.99 | — |

## Τεχνική που Προσομοιώθηκε

Εκτελέστηκαν δύο σαρώσεις από το μηχάνημα-επιτιθέμενο στην Kali:

1. **Σάρωση θυρών με αναγνώριση έκδοσης:**
   ```
   nmap -sV -p 1-1000 192.168.56.20
   ```
   Αποτέλεσμα: όλες οι 1000 θύρες που σαρώθηκαν εμφανίστηκαν ως `filtered` — το Windows Firewall απέρριψε σιωπηλά όλα τα probes σε αυτό το εύρος.

2. **Επιθετική σάρωση (αναγνώριση OS, αναγνώριση έκδοσης, scripts, traceroute):**
   ```
   nmap -A 192.168.56.20
   ```
   Αποτέλεσμα: η θύρα **3389/tcp (RDP)** βρέθηκε ανοιχτή, και τα scripts `rdp-ntlm-info` και `ssl-cert` του Nmap εξήγαγαν σημαντικές πληροφορίες απευθείας από το banner/TLS handshake της υπηρεσίας RDP, **χωρίς να χρειαστεί επιτυχής σύνδεση**:
   - Hostname: `WIN11-VICTIM`
   - NetBIOS domain και όνομα υπολογιστή
   - Έκδοση προϊόντος Windows: `10.0.26100` (Windows 11)
   - Ημερομηνίες ισχύος πιστοποιητικού SSL
   - Ώρα συστήματος του στόχου (χρήσιμη για χρονισμό επιθέσεων βασισμένο σε clock-skew)
   - Αποτύπωμα OS: Microsoft Windows 10/11

## Αποδεικτικά Στοιχεία

- **Windows Firewall log** (`C:\Windows\System32\LogFiles\Firewall\pfirewall.log`), φιλτραρισμένο στην IP του επιτιθέμενου:
  ```
  Get-Content "C:\Windows\System32\LogFiles\Firewall\pfirewall.log" | Select-String "192.168.56.30"
  ```
  Έδειξε πολλαπλές καταχωρήσεις `DROP TCP` στις θύρες 445, 139, και 135 (probes SMB/RPC) και πολλαπλές καταχωρήσεις `DROP ICMP` (τύπος 8 — echo request, που χρησιμοποιείται στην ανίχνευση hosts του Nmap), όλες με timestamps που ταιριάζουν με τις δύο σαρώσεις.

- **Ερώτημα στο dashboard του Wazuh** `agent.name: WIN11-VICTIM AND location: *pfirewall*` για το χρονικό διάστημα της σάρωσης επέστρεψε **"No results match your search criteria"** — επιβεβαιώνοντας ότι, παρόλο που το firewall log παρακολουθούνταν ενεργά από τον agent, κανένα αντίστοιχο event δεν έφτασε στον δείκτη (indexer) του Wazuh.

## Ανάλυση

Αυτό το σενάριο παρήγαγε ένα **αρνητικό αποτέλεσμα εντοπισμού**, το οποίο αποτελεί από μόνο του το κύριο εύρημα.

**Επιβεβαιώθηκε: το firewall του host λειτούργησε ως προληπτικός μηχανισμός ελέγχου.** Όλες οι 1000 θύρες που σαρώθηκαν στην πρώτη εκτέλεση φιλτραρίστηκαν, και ακόμα και στη δεύτερη, πιο επιθετική σάρωση, μόνο η σκόπιμα εκτεθειμένη θύρα RDP απάντησε. Αυτό είναι συνεπές με το INC-001, όπου το RDP κρατήθηκε σκόπιμα ανοιχτό και έγινε το σημείο εισόδου για μια επιτυχημένη επίθεση brute force — η αναγνώριση εδώ ουσιαστικά επιβεβαίωσε ξανά την ίδια εκτεθειμένη επιφάνεια επίθεσης.

**Επιβεβαιώθηκε: η ίδια η εκτεθειμένη υπηρεσία RDP διαρρέει πληροφορίες χρήσιμες για αναγνώριση** (hostname, domain, έκδοση OS, ημερομηνίες πιστοποιητικού) μέσω μη αυθεντικοποιημένων banners σε επίπεδο πρωτοκόλλου, πριν χρειαστούν καθόλου credentials. Ένας επιτιθέμενος δεν χρειάζεται επιτυχή σύνδεση για να ξεκινήσει να προφιλάρει τον στόχο.

**Κύριο κενό εντοπισμού που εντοπίστηκε:** παρόλο που το Windows Firewall logging είχε ενεργοποιηθεί ρητά (`Set-NetFirewallProfile -LogBlocked True`) και ο Wazuh agent είχε ρυθμιστεί να παρακολουθεί το αρχείο log που προέκυψε (επιβεβαιώθηκε στο `ossec.log`: *"Analyzing file: ... pfirewall.log"*), **κανένα αντίστοιχο alert, ούτε καν ακατέργαστη καταχώρηση log, δεν εμφανίστηκε στο dashboard του Wazuh.** Αυτό διερευνήθηκε και εντοπίστηκε ως **κενό decoder**: το προεπιλεγμένο ruleset του Wazuh δεν περιλαμβάνει decoder ικανό να αναλύσει τη native μορφή του Windows Firewall log (μια μορφή τύπου W3C-extended-log-file), άρα ακόμα κι αν ο agent διαβάζει και προωθεί το αρχείο, η πλευρά του server δεν έχει κανόνα να ερμηνεύσει ή να ευρετηριάσει το περιεχόμενό του.

Αυτό διαφέρει από τα κενά εντοπισμού που εντοπίστηκαν στα INC-002 και INC-003, τα οποία προκλήθηκαν από **απενεργοποιημένες ρυθμίσεις audit/logging των Windows** (πρόβλημα ρύθμισης, διορθώσιμο με ενεργοποίηση της σωστής ρύθμισης). Αυτό το κενό προκαλείται από **έλλειψη decoder/κανόνα στην πλευρά του Wazuh server** — περιορισμός του ίδιου του εργαλείου που δεν μπορεί να διορθωθεί μόνο με ρύθμιση του endpoint, και θα απαιτούσε είτε ανάπτυξη custom decoder/rule, είτε εντελώς διαφορετική προσέγγιση παρακολούθησης (βλ. Προτεινόμενες Ενέργειες).

Αυτό αποτελεί σημαντικό, ρεαλιστικό δίδαγμα για SOC: **η ενεργοποίηση μιας πηγής log είναι αναγκαία αλλά όχι επαρκής για τον εντοπισμό** — το SIEM πρέπει επίσης να διαθέτει decoder/κανόνα ικανό να κατανοήσει τη μορφή αυτού του log, αλλιώς τα δεδομένα συλλέγονται χωρίς κανένα όφελος.

## Προτεινόμενες Ενέργειες

1. Ανάπτυξη προσαρμοσμένου decoder και κανόνων για το Wazuh ειδικά για τη native μορφή του Windows Firewall log (`pfirewall.log`), ώστε να αναλύονται οι καταχωρήσεις `DROP`/`ALLOW` και να δημιουργούνται alerts σε μοτίβα ενδεικτικά σάρωσης (π.χ. πολλές διαφορετικές θύρες-προορισμού από μία πηγή IP σε σύντομο χρονικό διάστημα).
2. Ως πιο κλιμακώσιμη εναλλακτική από την ανάλυση τοπικών firewall logs, ανάπτυξη δυνατότητας εντοπισμού σε επίπεδο δικτύου (π.χ. Suricata ενσωματωμένο με Wazuh, ή αποκλειστικός αισθητήρας NIDS/NTA) σε ένα σημείο συμφόρησης του δικτύου, καθώς οι host-based agents από μόνοι τους έχουν θεμελιώδη τυφλά σημεία για κίνηση που δεν φτάνει ποτέ σε log επιπέδου εφαρμογής.
3. Περιορισμός της έκθεσης RDP μόνο στα μηχανήματα/δίκτυα που το χρειάζονται πραγματικά, και απενεργοποίηση ή απόκρυψη της διαρροής πληροφοριών σε επίπεδο πρωτοκόλλου όπου είναι δυνατό (π.χ. μέσω περιορισμών σύνδεσης RDP, Network Level Authentication, ή τοποθέτηση του RDP πίσω από VPN/jump host) ώστε να μειωθεί η αξία της αναγνώρισης μέσω banner-grabbing.
4. Περιοδική επαλήθευση ότι οι ρυθμίσεις "ενεργοποιημένου logging" (NTFS auditing, firewall logging, PowerShell logging, κλπ) πραγματικά καταλήγουν σε **ευρετηριασμένα, συναγερμοποιήσιμα δεδομένα** στο SIEM — όχι απλώς επιβεβαίωση ότι ο agent διαβάζει το αρχείο, καθώς η συλλογή χωρίς σωστή αποκωδικοποίηση δίνει ψευδή αίσθηση ασφάλειας.
5. Εξέταση εντοπισμού βασισμένου σε ρυθμό ή κατώφλι (rate/threshold-based detection) σε επίπεδο firewall/δικτύου (π.χ. πολλές προσπάθειες σύνδεσης σε πολλές διαφορετικές θύρες από την ίδια πηγή μέσα σε δευτερόλεπτα) ως εναλλακτική λύση ανεξάρτητη από decoder για τον εντοπισμό σαρώσεων.

## Διδάγματα (Σημειώσεις Lab)

- Η σημαία `-A` του Nmap εξήγαγε ουσιαστικές πληροφορίες για το μηχάνημα (hostname, domain, έκδοση OS, ισχύ πιστοποιητικού) από μία μόνο ανοιχτή θύρα RDP χωρίς καμία αυθεντικοποίηση — μια υπενθύμιση ότι ακόμα και μία εκτεθειμένη υπηρεσία έχει αξία αναγνώρισης.
- Η ενεργοποίηση του Windows Firewall logging (`Set-NetFirewallProfile -LogBlocked True`) και η επιβεβαίωση ότι ο Wazuh agent διαβάζει ενεργά το αρχείο που προκύπτει (μέσω `ossec.log`) **δεν αποτελεί επαρκή απόδειξη ότι ο εντοπισμός θα λειτουργήσει** — ολόκληρος ο αγωγός επεξεργασίας (agent → server → decoder → rule → index) πρέπει να επαληθεύεται από άκρη σε άκρη.
- Το προεπιλεγμένο ruleset του Wazuh σε αυτό το lab έχει ισχυρή, out-of-the-box κάλυψη για τηλεμετρία βασισμένη στο Windows Event Log (όπως φάνηκε στα INC-001 έως INC-003), αλλά έχει σαφές κενό για τα native text logs του Windows Firewall, το οποίο θα απαιτούσε ανάπτυξη custom decoder για να κλείσει.
- Αυτό το σενάριο αποτελεί χρήσιμη αντίθεση με τα προηγούμενα τρία: στα INC-002 και INC-003, η ενεργοποίηση μιας ενσωματωμένης ρύθμισης audit των Windows ήταν αρκετή για να ξεκλειδώσει τον εντοπισμό. Στο INC-004, η ενεργοποίηση της πηγής log δεν ήταν αρκετή — αποδεικνύοντας ότι δεν έχουν όλα τα "κενά ορατότητας" την ίδια βασική αιτία ή την ίδια λύση.
